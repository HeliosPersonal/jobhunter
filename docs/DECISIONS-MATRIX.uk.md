# Матриця рішень — пульт переконфігурації JobHunter

> **Що це.** Кожне рішення, ухвалене при проєктуванні JobHunter, подане як список із 3–4 варіантів
> з позначеним обраним. Це не переказ [[00-overview/adr/0001-modular-monolith-three-deployables|ADR]] —
> це **керуючий документ**: щоб перебудувати систему під інші вимоги, треба пройтися цим файлом,
> перемкнути потрібні варіанти й переписати документи, зазначені в колонці «Ціна переходу».
>
> Англомовні першоджерела: [[00-overview/adr/0001-modular-monolith-three-deployables|15 системних ADR]],
> [[DECISION-LOG]], [[ARCHITECTURE-OPEN-DECISIONS]]. Де вони суперечать цьому файлу — **вони мають перевагу**,
> бо містять повний контекст.

## A. Продукт і межі

### D01 · Для кого система

**Радіус:** 🔴 · **Закріплено:** [[DECISION-LOG|D1]], [[CONTEXT]] інваріант 9

| # | Варіант | Статус | Чому | Ціна переходу |
|---|---|---|---|---|
| 1 | **Один Власник; репозиторій водночас портфоліо** | ✅ | Потреба реальна й одинична. Мультитенантність подвоїла б поверхню (tenancy, auth, онбординг) заради користувача, якого не існує | — |
| 2 | Мультитенантний SaaS від початку | ❌ | Колонка `tenant_id` у кожній таблиці та фільтр у кожному запиті — назавжди. Архітектура це **не забороняє** пізніше | 🔴 Схема + всі запити + auth + білінг |
| 3 | Один Власник, але без «рецензента» як аудиторії | ⚖️ | Дозволило б не писати документацію. Половина цінності проєкту — портфоліо, тож це самообман | 🟢 Просто перестати оновлювати docs |
| 4 | Кілька профілів однієї людини (backend / platform / AI) | 🔁 | Тригер: реальна потреба таргетувати різні ролі. Змінює `Match` з `(job, profile)` на `(job, persona)` | 🟠 F4 повністю + ранжування + дайджест |

## B. Архітектура і топологія

### D08 · Кількість процесів

**Радіус:** 🔴 · **Закріплено:** [[00-overview/adr/0001-modular-monolith-three-deployables|ADR-0001]]

| # | Варіант | Статус | Чому | Ціна переходу |
|---|---|---|---|---|
| 1 | **Модульний моноліт: 3 деплойменти (`Api`, `Worker`, `Telegram`), 9 логічних стадій через RabbitMQ** | ✅ | Справжні межі повідомлень і справжній backpressure без дев'яти подів на одного користувача. Розділення пізніше — зміна маніфесту, не переписування | — |
| 2 | Дев'ять мікросервісів, по одному на стадію | ❌ | Операційна вартість без вигоди при одному користувачі. Обробники вже спілкуються лише через `JobHunter.Contracts` | 🟡 Новий хост + маніфест на стадію — **свідомо дешево** |
| 3 | Один процес, стадії як виклики методів | ❌ | Життєвий цикл Batch API триває годинами — межі стадій мають бути довговічними, а не кадрами стека | 🔴 Втрата відновлюваності |
| 4 | Два деплойменти (`Api` + все інше) | ⚖️ | Telegram long-poll має бути одним споживачем, і його падіння не повинно валити пайплайн | 🟡 Об'єднати хости |

### D09 · Транспорт між стадіями

**Радіус:** 🟠 · **Закріплено:** [[00-overview/adr/0002-rabbitmq-wolverine-transport|ADR-0002]]

| # | Варіант | Статус | Чому | Ціна переходу |
|---|---|---|---|---|
| 1 | **RabbitMQ + Wolverine (з EF Core outbox/inbox)** | ✅ | Брокер уже є в кластері. Wolverine дає discovery обробників, політики ретраїв і — вирішально — транзакційний outbox «з коробки» | — |
| 2 | RabbitMQ + MassTransit | ⚖️ | Цілком робоча альтернатива; outbox важчий, а м'язова пам'ять команди — Wolverine | 🟡 Переписати реєстрацію + сигнатури обробників |
| 3 | Kafka | ❌ | Немає вимоги replay чи log-compaction при ~300 повідомленнях на день. Додає компонент кластера, потрібний лише нам | 🟠 Новий компонент + семантика offset |
| 4 | Тільки PostgreSQL (`FOR UPDATE SKIP LOCKED`) | ⚖️ | Життєздатно на цьому обсязі, але твердження «event-driven архітектура» стало б питанням тлумачення. Брокер безкоштовний | 🟠 Своя черга + свій планувальник споживачів |

### D10 · Гарантія публікації подій

**Радіус:** 🟠 · **Закріплено:** [[00-overview/adr/0007-transactional-outbox|ADR-0007]]

| # | Варіант | Статус | Чому | Ціна переходу |
|---|---|---|---|---|
| 1 | **Транзакційний outbox + inbox Wolverine, плюс доменний ключ ідемпотентності на кожній стадії** | ✅ | Без нього зміна стану і публікація події — два записи: або подія втрачена (пайплайн тихо стає), або подія без стану | — |
| 2 | Публікувати після `SaveChangesAsync` | ❌ | Класична проблема подвійного запису. При одному Run на добу втрачена подія = втрачений день, і помітять о 07:00 | 🟢 Прибрати `[Transactional]` — **не робити** |
| 3 | Власна таблиця outbox + polling relay | ⚖️ | Те саме, але писати самому. Wolverine це вже вміє | 🟡 ~200 рядків інфраструктури |
| 4 | Ідемпотентність тільки на рівні домену, без outbox | ⚖️ | Захищає від дублювання, але не від **втрати** події | 🟠 Втрата гарантії доставки |

| 4 | LLM-фолбек на нерозпізнаний ввід | ❌ | Ставить очікування загальної компетентності, яке продукт не виконує. І кладе ймовірнісний крок на шлях до `/run` і `/cv` — тобто до витрат грошей і до інвалідації дня matching | 🟡 Реєстр уже дає цільовий набір, якщо повертатись |

**Тригер повернення до варіанта 4:** частка нерозпізнаних команд стабільно вище 5% ([[features/f10-telegram-commands/PRD|F10 PRD]] §7) — тоді intent-routing **по наявному каталогу** буде найменшим наступним кроком, і це буде новий ADR, а не тиха зміна.

## J. Сценарії переконфігурації

Готові рецепти: які рішення перемкнути разом, щоб отримати іншу систему.

### J1 · «Зробити дешевше вдвічі»

| Перемкнути | З → На |
|---|---|
| D24 Matching | `Deep` → `Cheap` |
| P05 стеля | `$2.00` → `$0.75` |
| P08 карток | `10` → `6` |
| D23 Company research | вимкнути F8 (`0` досьє/день) |
| P24c частка в matching | `40%` → `25%` (агресивніший pre-filter) |

**Наслідок:** ~$12/міс замість ~$31. Якість matching помітно впаде — це і є плата.
Порівняння повного розкладу — [[operations/infrastructure]] §8.

### J2 · «Зробити мультикористувацьким SaaS»

| Перемкнути | З → На |
|---|---|
| D01 | Один Власник → мультитенант |
| D31 | Allowlist → OAuth-звʼязка |
| D03 | Telegram → Telegram + вебзастосунок |
| D37 | helios → керований кластер |

**Наслідок:** 🔴 переписування. Зачіпає схему (tenant_id всюди), auth, білінг, ізоляцію вартості
LLM на користувача. Реалістично — новий проєкт із запозиченим доменним ядром.

### J3 · «Прибрати LLM повністю»

| Перемкнути | З → На |
|---|---|
| D21 | Batch API → без моделі |
| D32 | Частотне зважування ← лишається (воно не LLM) |
| Видалити | F3, F4 (matching), F8 |
| D42 | Пошук стає головним інтерфейсом |

**Наслідок:** залишається якісний ATS-агрегатор із дедуплікацією і пошуком. Точність впаде до рівня
фільтрів (підхід A з [[00-overview/idea-brief|idea-brief]] §7). Приблизно 40% коду лишається робочим.

### J4 · «Перенести в хмару з HA»

| Перемкнути | З → На |
|---|---|
| D37 | helios → AKS/EKS |
| D11 | 1 репліка → розділити per-stage (варіант 3) |
| D38 | лишається Kustomize; додати GitOps (D38 варіант 3) |
| D14 | PostgreSQL → керований PostgreSQL |
| D40 | лишається без змін — OTLP уже портативний |

**Наслідок:** 🟠 1–2 тижні. Основна робота — розподілене блокування Hangfire і винесення
оркестрації Run з припущення про сингтон.

### J5 · «Максимальна точність, вартість не важлива»

| Перемкнути | З → На |
|---|---|
| D24 Enrichment | `Cheap` → `Deep` |
| P05 стеля | `$2.00` → `$10.00` |
| D21 | додати escalation-тир для неоднозначних елементів |
| P31 вікно re-match | `30` → `90 днів` |
| D34 | зниження ваги → без фільтрації взагалі |

**Наслідок:** ~$110/міс (дорогий тир на `claude-opus-5` подвоює matching, enrichment переходить на
Sonnet 5, pre-filter вимкнено). Очікуване покращення `precision@10` — неперевірене; варте
експерименту після того, як зʼявиться базова лінія M4.
