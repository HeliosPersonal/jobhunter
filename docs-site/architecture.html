How it is built

Architecture

One repository, three deployables, nine logical stages communicating over durable message boundaries. Every external dependency sits behind a port; adding an ATS provider is a new class, not a change to the pipeline.

Inside the boundary

C4 container — three deployables, one store

The Worker is the engine: Hangfire schedules and all nine stage consumers run in it, as a single replica by design (Recreate strategy). The Api is a stateless Keycloak-protected read/admin surface. The Telegram host is inbound-only — it long-polls, handles commands and callbacks, and publishes what the Owner did.

The wire contracts

Event catalog — the pipeline as messages

Stages never call each other directly; they publish past-tense events on RabbitMQ, one queue per consuming deployable, one dead-letter queue per stage. Wolverine's EF Core outbox makes state-change and publication atomic — no duplicate spend, no duplicate delivery.

The main event chain (producer → consumer) 
flowchart TB
  hang["Hangfire 6h"] -->|SourceFetchRequested| disc["FetchSourceHandler"]
  disc -->|RawPostingIngested| norm["NormalizationHandler"]
  norm -->|JobNormalized| dedup["DeduplicationHandler"]
  dedup -->|JobDiscovered| idx["JobIndexRequestTranslator → SearchIndexingHandler"]
  hang2["Hangfire daily"] -->|StartDailyRun| orch["RunOrchestrator"]
  orch -->|EnrichmentSubmissionDue| enr["EnrichmentSubmitHandler"]
  enr -->|BatchPollDue| poll["BatchPollHandler"]
  poll -->|EnrichmentCompleted| match["MatchingSubmitHandler"]
  match -->|MatchingPollDue| mpoll["MatchingPollHandler"]
  mpoll -->|MatchingCompleted| rank["RankingHandler"]
  rank -->|RankingCompleted| report["DigestAssembler"]
  rank -.->|ResearchRequested (designed, not yet wired)| research["(research fan-out)"]
  report -->|DigestReady| marker["(assembled marker)"]
  hang3["Hangfire 07:00 Kyiv"] -->|DigestDeliveryDue| deliver["DeliveryHandler"]
  deliver -->|DigestDelivered| metrics["(Telemetry — no consumer)"]

Owner-side and exception events close the loop: OwnerActionRecorded is consumed by OwnerActionHandler (its producer — the Applied tap — is not yet wired); PreferenceModelUpdated (weekly fitting job) feeds the next Run's ranking; RunCostAborted and SourceQuarantined are published, and a reduced digest still ships — the Owner-alert consumers are recorded inline via Telemetry, not yet wired to Telegram.

Усередині межі

C4 контейнери — три розгортання, одне сховище

Worker — це двигун: Hangfire-розклади та всі дев'ять споживачів стадій працюють у ньому, як єдина репліка за задумом (стратегія Recreate). Контракти на дроті

Каталог подій — конвеєр як повідомлення

Стадії ніколи не викликають одна одну напряму; вони публікують події у минулому часі в RabbitMQ, одна черга на споживача, одна dead-letter черга на стадію. EF Core outbox від Wolverine робить зміну стану й публікацію атомарними — без подвійних витрат чи подвійної доставки.
