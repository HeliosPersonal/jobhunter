Runbook & onboarding

Run it

A day, end to end

Discovery runs around the clock; one nightly Run turns the day's new jobs into a ranked digest; the Owner's morning taps become tomorrow's ranking. Here is the whole loop, in the order it happens.

All day

Discovery → Normalization → Deduplication

Every six hours Hangfire asks each Source to fetch. The verbatim payload is stored as an immutable RawPosting; normalization parses it into a candidate Job; deduplication collapses the same vacancy seen on two boards into one canonical Job by its Fingerprint.

From a board fetch to a canonical Job 
sequenceDiagram
  participant H as Hangfire (6h)
  participant D as FetchSourceHandler
  participant S as ATS board
  participant N as NormalizationHandler
  participant X as DeduplicationHandler
  participant I as SearchIndexingHandler
  H->>D: SourceFetchRequested
  D->>S: GET board (robots + rate budget honoured)
  S-->>D: raw JSON
  D->>D: store immutable RawPosting
  D->>N: RawPostingIngested
  N->>N: parse title, location, salary, remote policy
  N->>X: JobNormalized
  X->>X: compute Fingerprint, merge into earliest Job
  X->>I: JobDiscovered (index the canonical Job)

A Source that returns 403/429 twice in a row is quarantined, not retried harder — and the Owner is paged.

Overnight

One Run assembles the morning

The Run walks its state machine: enrich the day's jobs, match them against the CV, rank with the current preference weights, research the top companies, assemble the digest. Each LLM stage submits a Batch and waits for the poller — never a synchronous call.

The nightly Run 
sequenceDiagram
  participant H as Hangfire (daily)
  participant R as RunOrchestrator
  participant E as EnrichmentSubmitHandler
  participant P as BatchPollHandler
  participant M as MatchingSubmitHandler
  participant K as RankingHandler
  participant Rep as DigestAssembler
  H->>R: StartDailyRun
  R->>R: RunStarted (audit marker)
  R->>E: EnrichmentSubmissionDue
  E->>P: BatchPollDue
  P-->>M: EnrichmentCompleted
  M->>P: MatchingPollDue (CV crosses here, once)
  P-->>K: MatchingCompleted
  K->>Rep: RankingCompleted (Scores)
  Rep->>Rep: DigestReady (assembled marker)
The cost ceiling is checked before each Batch submission. If the estimate would breach it, the client is not called, the Run becomes CostAborted, and a reduced digest still ships.

Why a crash is survivable

Resumability, concretely

Suppose the Worker dies mid-matching. On restart, the Run resumes from its last durable state. Enrichments already written are not recomputed — re-running a stage supersedes by (job_id, run_id, stage). Batches already submitted are polled, not re-submitted. The crash matrix tests eight kill points and asserts exactly one batch submission at each.

Crash and resume during matching 
sequenceDiagram
  participant M as MatchingSubmitHandler
  participant DB as Postgres
  participant A as Anthropic Batches
  participant P as MatchingPollHandler
  M->>A: submit matching Batch
  M->>DB: persist Batch id + Estimated cost
  Note over M,DB: Worker crashes here
  P->>DB: on restart, find outstanding Batch
  P->>A: poll batch status (no re-submit)
  A-->>P: ended → results
  P->>DB: persist Matches (supersede by job/run/stage)

07:00, and after

Delivery, then the feedback loop

At 07:00 Europe/Kyiv a separate Hangfire trigger fires DigestDeliveryDue; the DeliveryHandler renders the digest into Telegram messages, idempotently — a (run_id, chat_id, card_key) triple is delivered at most once. When the Owner taps Open, Ignore, Save or Applied, the bot records a Signal; a weekly fitting job turns Signals into new weights that the next Ranking uses.

Delivery and the weekly preference loop 
sequenceDiagram
  participant H as Hangfire (07:00 Kyiv)
  participant Del as DeliveryHandler
  participant TG as Telegram
  participant O as Owner
  participant Sig as SignalHandler
  participant Fit as PreferenceLearner (weekly)
  participant Rank as RankingHandler
  H->>Del: DigestDeliveryDue
  Del->>TG: render Cards (idempotent by card_key)
  TG->>O: the 07:00 digest
  O->>TG: tap Open / Ignore / Save / Applied
  TG->>Sig: OwnerActionRecorded
  Sig->>Sig: store Signal with job facts
  Fit->>Rank: PreferenceModelUpdated (explainable weights)

Preference learning never hard-filters silently: a suppressed Job carries a recorded reason, and the digest reports how many were suppressed and why.

Запуск

День, від А до Я

Discovery працює цілодобово; один нічний Run перетворює нові вакансії дня на ранжований дайджест; ранкові дотики власника стають завтрашнім ранжуванням. Ось увесь цикл, у порядку, як він відбувається.

Цілий день

Discovery → Normalization → Deduplication

Кожні шість годин Hangfire просить кожен Source отримати дані. Дослівний payload зберігається як незмінний RawPosting; нормалізація парсить його в кандидатну Job; дедуплікація зливає ту саму вакансію з двох дошок в одну канонічну Job за її Fingerprint.

Від отримання дошки до канонічної Job 
sequenceDiagram
  participant H as Hangfire (6 год)
  participant D as FetchSourceHandler
  participant S as ATS-дошка
  participant N as NormalizationHandler
  participant X as DeduplicationHandler
  participant I as SearchIndexingHandler
  H->>D: SourceFetchRequested
  D->>S: GET дошки (robots + бюджет швидкості дотримані)
  S-->>D: сирий JSON
  D->>D: зберегти незмінний RawPosting
  D->>N: RawPostingIngested
  N->>N: парсинг назви, локації, зарплати, remote
  N->>X: JobNormalized
  X->>X: обчислити Fingerprint, злити в найранішу Job
  X->>I: JobDiscovered (індексувати канонічну Job)

Source, що двічі поспіль повертає 403/429, потрапляє в карантин, а не переопитується агресивніше — і власника сповіщають.

Уночі

Один Run збирає ранок

Run проходить свій автомат: збагатити вакансії дня, зіставити з CV, ранжувати за поточними вагами вподобань, дослідити топ-компанії, зібрати дайджест. Кожна LLM-стадія відправляє Batch і чекає на poller — ніколи синхронний виклик.

Нічний Run 
sequenceDiagram
  participant H as Hangfire (щодня)
  participant R as RunOrchestrator
  participant E as EnrichmentSubmitHandler
  participant P as BatchPollHandler
  participant M as MatchingSubmitHandler
  participant K as RankingHandler
  participant Rep as DigestAssembler
  H->>R: StartDailyRun
  R->>R: RunStarted (аудит-маркер)
  R->>E: EnrichmentSubmissionDue
  E->>P: BatchPollDue
  P-->>M: EnrichmentCompleted
  M->>P: MatchingPollDue (CV перетинає тут, один раз)
  P-->>K: MatchingCompleted
  K->>Rep: RankingCompleted (Scores)
  Rep->>Rep: DigestReady (зібраний маркер)
Стеля вартості перевіряється перед кожною відправкою Batch. Якщо оцінка її перевищить, клієнт не викликається, Run стає CostAborted, а скорочений дайджест усе одно виходить.

Чому збій переживається

Відновлюваність конкретно

Припустімо, Worker падає посеред matching. При перезапуску Run відновлюється з останнього довговічного стану. Уже записані Enrichment не переобчислюються — повторний запуск стадії заміщує за (job_id, run_id, stage). Уже відправлені Batch опитуються, а не відправляються знову. Crash-матриця тестує вісім точок збою і стверджує рівно одну відправку batch у кожній.

Збій і відновлення під час matching 
sequenceDiagram
  participant M as MatchingSubmitHandler
  participant DB as Postgres
  participant A as Anthropic Batches
  participant P as MatchingPollHandler
  M->>A: відправити matching Batch
  M->>DB: зберегти id Batch + Estimated вартість
  Note over M,DB: Worker падає тут
  P->>DB: при перезапуску знайти невиконаний Batch
  P->>A: опитати статус batch (без повторної відправки)
  A-->>P: ended → результати
  P->>DB: зберегти Matches (заміщення за job/run/stage)

07:00 і після

Доставка, потім цикл зворотного зв'язку

О 07:00 за Києвом окремий тригер Hangfire запускає DigestDeliveryDue; DeliveryHandler рендерить дайджест у Telegram-повідомлення, ідемпотентно — трійка (run_id, chat_id, card_key) доставляється щонайбільше раз. Коли власник тисне Open, Ignore, Save чи Applied, бот фіксує Signal; щотижневе завдання перетворює Signals на нові ваги, які використовує наступне Ranking.

Доставка і щотижневий цикл вподобань 
sequenceDiagram
  participant H as Hangfire (07:00 Київ)
  participant Del as DeliveryHandler
  participant TG as Telegram
  participant O as Owner
  participant Sig as SignalHandler
  participant Fit as PreferenceLearner (щотижня)
  participant Rank as RankingHandler
  H->>Del: DigestDeliveryDue
  Del->>TG: рендер Cards (ідемпотентно за card_key)
  TG->>O: дайджест о 07:00
  O->>TG: дотик Open / Ignore / Save / Applied
  TG->>Sig: OwnerActionRecorded
  Sig->>Sig: зберегти Signal з фактами вакансії
  Fit->>Rank: PreferenceModelUpdated (пояснювані ваги)

Навчання вподобань ніколи не фільтрує тихо: придушена Job несе зафіксовану причину, а дайджест повідомляє, скільки придушено і чому.
